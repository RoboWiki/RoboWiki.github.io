refactor: 为开源共建重构架构 —— pipeline/tools/schema 三层 + 测试 + 门禁

原来 scripts/ 下 30 个脚本，其中 16 个都能写 data/catalog：谁最后跑谁说话。
单人开发靠记忆兜得住，多人协作必出事故。这次按职责切开，并把「怎么参与」
写成可执行的规则。

一、目录按职责分层
  pipeline/   确定性构建（唯一能产生产物的地方）
    load.py         读 data/（原 load_catalog）
    validate.py     数据闸门（原 check_data）
    build_site.py   生成站点内容与 catalog.json（原 build_wiki）
    ingest_ratings.py / ingest_reviews.py   issue -> 快照
    __main__.py     python -m pipeline validate|build|all
  tools/      一次性迁移脚本（会改数据，README 标明别随手跑）
  schema/     JSON Schema —— PR、issue 表单、API 共用同一份契约
  tests/      构建链测试（原来 80 个测试全在后端，pipeline 零覆盖）

二、一条命令进出
  python -m pipeline all     校验 + 生成
  python -m pytest           构建链 + API，90 项
  make validate/build/test/site/serve

三、补上零覆盖的那块（10 项新测试）
  · 闸门真的会红：喂一条 mass=740kg 的零件必须失败，不能安静放过
  · loader 优先级与 id 唯一性（id 重复会让评分/讨论错位）
  · offers 必须带 demo 标记与获取条件
  · part_slug 稳定且 ASCII（URL 变了 = 外链与 giscus 讨论全断）
  · 侧边栏必须列出全部厂商 —— 上次「rows=[] 覆盖全局变量」那个 bug 的回归
  · catalog.json 条数、页数、站内死链扫描

四、PR 门禁（.github/workflows/pr-gate.yml）
  数据闸门 -> schema 校验（jsonschema）-> pytest -> 站点构建
  刻意不加 --strict：库里有 25 条「真话式警告」（只公布额定扭矩等），
  strict 会让每个 PR 一律变红，门禁等于废掉。

五、开源生态需要的其他东西
  · schema/*.schema.json + README（改字段先改这里）
  · pyproject.toml（pip install -e . 可用，pytest 配置收口）
  · LICENSE（MIT）
  · docs/ARCHITECTURE.md：GitHub 管事实、服务器管流量，读走产物写走服务
  · tools/README.md：哪些脚本会改数据、哪些是归档
  · README 重写：三分钟上手、目录、参与方式、现状（诚实版）
  · CODEOWNERS 跟上新路径
