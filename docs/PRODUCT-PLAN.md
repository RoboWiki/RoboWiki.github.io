# RoboWiki 产品定位、架构与双端功能方案

> 2026-11-06 · 基于本仓实测审计 + 4 路外部调研（论坛社区 / 电商目录 / AI 网关 / 硬件文档）
>
> **结论先行**：继续做「可追溯的机器人工程知识库」，**不做自营商城、不做通用论坛、不做模型网关**。
> 网页端负责深度阅读、检索、对比与贡献；小程序端负责现场工具与轻互动；后端保持唯一写域。
> 双端通过同一套信息架构、设计 token、内容模型与功能命名收敛体验，而不是把网页压成小程序或反过来。

---

## 0. 一页结论

| 问题 | 结论 |
|---|---|
| 项目到底做什么 | 机器人制作全流程的**可信选型 + 可复现方案 + 经验社区** |
| 网页端定位 | 深度阅读与 SEO 主站：部件库、方案库、学习路径、社区、采购渠道 |
| 小程序端定位 | 现场工具与轻互动：查件、对比、扫一扫、评分、讨论、通知、投稿 |
| 后端定位 | 唯一写域与身份中心；目录只读投影，UGC 只走 `/api/v1` |
| 要不要做商城 | **不做**。部件目录 + 采购外链 + BOM 兼容矩阵，不碰购物车/支付/库存 |
| 要不要做 AI 中转站 | **不做**。只做薄层「可引用选型助手」：RAG + 引用回链 + 拒答 |
| 要不要换掉 Astro | **不换**。Astro + React 19 岛已满足「React 组件层」；604 页静态站改 SPA 收益低、风险高 |
| 当前最大问题 | 网页 47 个路由 / 604 页，小程序只有 5 页；导航 4 项 vs 实际内容严重不匹配；每页都挂讨论区，阅读与讨论混在一起 |

一句话定位：**每一步都有来源，每一套都能复现。**

## 1. 现状审计（本机实测）

### 1.1 规模与技术栈

| 端 | 技术 | 规模 |
|---|---|---|
| 网页端 `apps/web` | Astro 7.4 + React 19 岛 + Tailwind 4 + antd 6 + react-query | **47 个 `.astro` 路由文件 / 604 个构建页** |
| 小程序端 `apps/app` | Taro 4.3 + React 19（H5 + 微信小程序） | **5 个页面**：首页(目录)、部件、登录、账号、投稿 |
| 后端 `backend` | FastAPI + SQLModel + Alembic | **17 个路由模块 / 约 70 个端点** |
| 共享层 | `packages/tokens`、`packages/core` | 设计 token + API 客户端/类型 |
| 数据 | `RoboWiki` 仓 `data-v2026.11.6` | 346 部件 / 21 整机 / 27 材料 / 9 工艺 / 639 ID / 439 图 |

### 1.2 双端能力差异

| 能力 | 网页端 | 小程序端 | 差距 |
|---|---|---|---|
| 首页 / 品牌叙事 | ✅ 完整落地页 | ❌ 首屏直接是部件列表 | 小程序没有「产品感」 |
| 部件库 | ✅ 搜索 + 品类 + 等级 + 开源 + 对比托盘 | ⚠️ 搜索 + 品类 chips | 筛选维度少一半 |
| 部件详情 | ✅ 参数 / 来源 / 评分 / 讨论 | ✅ 参数 / 评分 / 讨论 | 布局、信息顺序不同 |
| 参数对比 2–4 件 | ✅ `/compare` | ❌ | 移动端最需要的能力缺失 |
| 方案库 / 整机 | ✅ `/builds`、`/robots` | ❌ | 无法在手机上看看得懂的方案 |
| 学习路径 / 指南 | ✅ `/start`、`/learn` | ❌ | 新用户没有入口 |
| 材料与工艺 | ✅ `/materials` | ❌ | — |
| 采购渠道 | ✅ `/suppliers` | ❌ | — |
| 社区流 / 帖子 / 用户页 | ✅ React 岛 | ❌ 仅部件级评论 | 社区在移动端不存在 |
| 通知 | ✅ 账号岛 | ✅ 账号页 | 基本对齐 |
| 投稿纠错 | ✅ Web DataFix | ✅ submit | 口径基本一致 |
| 深色模式 | ✅ 主题切换 + `.dark` | ❌ `app.css` 硬编码 `#0f172a` | 视觉体系断裂 |
| 底部导航 | — | ❌ 没有 `tabBar` | 只有栈式跳转，找不到功能 |

### 1.3 UI 不一致的具体证据

1. **同一套 token，两套实现**：`packages/tokens` 共享 `--rw-*`，但网页用 Tailwind `@theme` 映射，小程序在 `apps/app/src/app.css` 手写 314 行 `.rw-*` 组件；按钮、输入、列表、空态各写一遍。
2. **小程序硬编码颜色**：`apps/app/src/app.css:5` 写死 `color: #0f172a`，没有用 `var(--rw-ink)`，token 改了小程序不跟。
3. **字体栈不同**：网页用 `var(--rw-font-sans)`（Inter / Noto Sans SC），小程序用系统字体栈，字重与行高观感不同。
4. **没有深色模式**：tokens 已定义 `page.dark`，但 `app.tsx` 没有主题落定逻辑，小程序始终浅色。
5. **首页语义不同**：网页首页是「定位 + 四条主路径 + 推荐部件」；小程序首页是「部件目录列表」。同一个产品，第一屏讲的事不一样。
6. **导航不同构**：网页主导航 4 项（学习/方案/部件/采购），小程序无 tabBar；两端都不把「社区」放进主导航。

### 1.4 内容混杂的根因

1. **导航与内容规模失配**：网页 47 个路由，主导航只有 4 项；社区、文档、工具、开源索引、贡献者、参数口径、来源清单全部藏在页脚或页内链接里，用户找不到。
2. **边界被打破**：`docs/DESIGN.md` 写的是「Astro 只读 / Taro 全写」，但现状是网页已有 community / post / u / admin / login 多个 React 岛并承担写操作；小程序仍只有 5 页。结果是「网页什么都有、小程序只有目录」。
3. **讨论区泛滥**：`apps/web/src/layouts/Base.astro:25` 的 `showComments` 让除少数工具页外的所有内容页都挂评论区，阅读正文与讨论混在一起，页面底部无限拉长。
4. **社区不是一等公民**：社区只能从首页卡片或部件页进入，主导航与页脚都没有入口；而社区恰恰是「经验沉淀」的核心。

### 1.5 后端契约问题

| 问题 | 证据 | 影响 |
|---|---|---|
| 同字段多写 | `packages/core/src/index.ts` 的 `PartSummary` 同时有 `subtype` / `subtype_label` / `subtypeLabel`、`price_cny` / `price`、`image_url` / `image`、`tauPeak` 等 | 前端要猜用哪个，契约漂移 |
| 定位描述过期 | `backend/app/main.py` 的 API 描述仍是「四足机器人选型 + 社区。选型是底座，互动是主体。」 | 与「全流程知识库」不一致 |
| 响应模型不全 | 部分路由未声明 `response_model`，SDK 生成会退化成 `unknown` | 客户端类型不可信 |
| 社区接口闲置 | 后端有 `/posts`、`/votes`、`/leaderboard`，小程序 `services/api.ts` 完全没调用 | 移动端社区能力浪费 |
| 版本头不统一 | 只有部分列表/详情回显 `data_version` | 缓存与追溯不一致 |

## 2. 外部对标结论

### 2.1 四类项目，分别学什么、不学什么

| 类别 | 代表 | 满足「React + >1k + 近期维护」 | 学什么 | 不学什么 |
|---|---|---|---|---|
| 论坛社区 | **bbs-go**（3,502★，React 19，2026-10 活跃） | ✅ 唯一全满足 | 讨论/问答/专栏三分、积分等级勋章、审核后台 | 纯时间流、无限 tag、签到打卡 |
| | Misago（2,780★，Django+htmx，React 15 遗留） | ❌ 前端不满足 | 无限级分类、rank×role×分类权限、审核队列 | 不复用代码 |
| | RoboMaster 官方论坛 / rcbbs（Discourse） | — | 「职能 × 兵种」双轴标签、被引用计数、内容形态分离 | 非 React 栈；不搬 Discourse |
| | ZJU Wiki（34★）/ robowalker_train（898★） | ❌ 热度/栈不满足 | 课程目录 + 作业 + 修订日志 + 教学反馈闭环 | 仅内容组织参考 |
| 电商目录 | **Vendure**（8,565★）/ **EverShop**（10,541★） | ✅ 但不需要商城内核 | Product / Variant / Facet / Collection 数据模型；facet 化参数 | 不嵌 commerce 内核、不做购物车/支付 |
| | Reaction（12,400★） | ❌ 已停更（2026-03） | — | 直接排除 |
| | **roboparts.cc** | 非 GitHub 项目 | **供应商中立的兼容性/选型层**：三态结论 + 证据字段 + BOM 兼容矩阵 | 它明确没有价格/库存/购物车，也不该有 |
| AI 网关 | **New API**（51,479★，React 19） | ✅ | 渠道优先级、自动重试/降级、成本计量 | **AGPL-3.0 + Section 7 署名**，不 fork |
| | **AxonHub**（5,435★，React 19） | ✅ | 请求级 trace：检索片段 → 模型 → 引用，逐项 token/成本 | 不把网关当产品主体 |
| | CoAI（9,345★） | ❌ 2026-03 后无实质提交 | Chat + 计费打包思路 | 不作为底座；RAG 在商业版 |
| | aifitlab.com | 非软件项目 | 作为 BOM / 元器件价格数据源 | 不是可选型组件 |
| 硬件文档 | Seeed wiki-documents（414★，Docusaurus + DocSearch） | ❌ 热度不足 | 参数表「Parameter / Value（含测试条件）」、资源按类型打标、`?tab=` 多读者视图 | 不换 Docusaurus |
| | Waveshare（MediaWiki） | — | 「按宿主平台分支」应收敛为兼容矩阵；FAQ 折叠 | 中英双站不互通、陈旧分支无过期标记 |
| | OpenELAB（GitBook） | — | 固定产品页骨架：介绍→特性→参数→引脚→尺寸→使用→注意 | 无仓库、不可控 |
| | locowiki（183★/5★） | ❌ 热度不足 | 内容仓/站点仓分离、dispatch 刷新索引、正文版本即 commit | 运行时拉 MD 的方案不搬 |
| | draft（193★） | ❌ | 参数表当**数据**而非文本；114 执行器目录拟合缺失参数 | 不是文档站 |

### 2.2 三条关键判断

1. **用户给定的「React + >1k + 近期维护」筛选，真正全满足的只有 bbs-go（社区）、Vendure/EverShop（电商）、New API/AxonHub（AI）。** 硬件文档类最高只有 414★，因此只能借 IA，不能当技术选型依据。
2. **RoboWiki 的差异化不在「商城」也不在「网关」，而在「参数级可追溯 + 方案级可复现」。** 这三类开源项目都不直接提供「答案带引用、参数可回指手册」的能力——这正是本项目的护城河。
3. **一切外部系统只做参考，不 fork 当底座。** New API 的 AGPL、Vendure/Reaction 的 GPL 与停更风险、Discourse 的 Ruby 栈，都会把项目拖进非核心维护。

## 3. 最终定位

### 3.1 一句话

> **RoboWiki：面向机器人部件的可追溯工程知识库。**
>
> 以参数可追溯的部件库为核心，先把「这个件到底怎么样、多少钱、谁用过」做扎实；选型台是试验工具，用于按构型试配 BOM；社区共建每个部件的实测与评价，再逐步打通机械—硬件—嵌入式—算法与系统集成的制作全链路，把参数、方案、采购与实测沉淀为可检索、可复现、可追溯的工程知识。
>
> 部件库与采购是当前主线；选型台为试验版，四层能力 + 系统集成是全链路骨架，按阶段补。
>
> 一句话：**每一步都有来源，每一套都能复现。**

### 3.2 目标人群与核心任务（JTBD）

| 人群 | 他们来做什么 | 关键路径 |
|---|---|---|
| RoboCon / RoboMaster 竞赛队 | 选型、算 BOM、复现方案、查踩坑、现场查件 | 搜索 → 部件详情 → 对比 → 方案 BOM → 复现记录 |
| 科研 / 教育工作者 | 找可信参数、做教学路径、引用来源 | 学习路径 → 指南 → 部件参数 + 来源 → 引用 |
| 开源开发者 | 找开源方案、看复现结果、贡献数据 | 开源索引 → 方案详情 → 复现记录 → 投稿 |
| 硬件厂商 / 渠道 | 被准确收录、被真实评价 | 部件页 → 来源核对 → 纠错 |

### 3.3 三层价值

| 层 | 价值 | 已有基础 |
|---|---|---|
| 可信选型 | 每个参数有来源等级（A/B/C）、核对状态、缺失写 `null` | `source_tier` / `verified` / `data-v*` |
| 可复现方案 | BOM + 步骤 + 交付物 + 复现结果（成/部分成/没成） | `builds`、`reproductions`、recipe schema |
| 经验社区 | 讨论挂件、问答可采纳、纠错进版本 | `posts`、`wiki_comments`、`submissions` |

### 3.4 明确不做

- ❌ 自营电商、购物车、支付、库存、佣金
- ❌ 通用论坛 / 纯时间流 / 签到打卡 / 无限版块
- ❌ AI 模型中转站 / 多租户计费网关
- ❌ 为「纯 React」把 604 页静态站改成 SPA
- ❌ 把厂商手册、商品图、第三方仓库内容当自有资产

### 4.1 总览

### 4.2 网页端：保留 Astro，做强「读 + 找 + 比」

- **保留 Astro 的理由**：604 个内容页、SEO、canonical/OG/JSON-LD、PWA、静态托管是核心资产；Astro 里已经跑 React 19 岛，满足「React 组件层」。
- **React 岛的边界**：只放交互密集区（搜索、筛选、对比、社区、账号、站务、评分快照），不要整页 hydration。
- **不做的迁移**：不改成 Next.js / Remix 全 SPA；如未来确需统一元框架，先写 ADR，再只迁移交互层，内容层保持静态。

### 4.3 小程序端：从「目录工具」升级为「现场助手」

- **5 个 tab**：`首页 / 部件 / 方案 / 社区 / 我的`（微信小程序 tabBar 上限 5）。
- **首页**：任务入口，不是原始列表——搜索框、扫一扫、最近浏览、热门部件、学习路径、方案入口。
- **部件**：目录 + 筛选 + 对比托盘（最多 4 件）。
- **方案**：整机列表 + 方案详情（BOM / 步骤 / 交付物 / 复现记录）。
- **社区**：信息流 + 帖子详情 + 问答（可采纳）。
- **我的**：账号、通知、我的投稿、深色模式、关于。
- **二级页**：登录、投稿纠错、部件详情、对比结果、学习文章、材料、渠道。

### 4.4 共享层：共享「契约」，不共享 DOM

`docs/DESIGN.md` 已明确「不共享 DOM 组件到小程序」，这个判断是对的。建议新增两个包：

| 包 | 内容 | 作用 |
|---|---|---|
| `packages/tokens`（已有） | `--rw-*` token + TS 常量 | 颜色/间距/字号/控件尺寸单一来源 |
| `packages/core`（已有） | API 客户端、类型、错误模型 | 两端同一套请求/重试/刷新 |
| **`packages/content`（新增）** | 导航、页面标题、空态/错误/加载文案、功能命名、能力矩阵 | 双端 IA 与文案只写一处 |
| **`packages/features`（新增）** | headless hooks：`useCatalog` / `usePart` / `useCompare` / `useRating` / `useComments` / `useSubmission` / `useNotifications` | 业务状态与副作用复用；各端只写渲染 |
| `packages/ui-web`（可选） | Tailwind + antd 的 Button/Input/Card/Badge/Chip/Empty/Error/Skeleton | 网页组件统一 |
| `packages/ui-taro`（可选） | Taro 版同 props 组件 | 小程序组件统一 |

**原则**：两端共享 token、类型、hooks、文案；不共享 DOM；组件用同一套 props 与状态机各自实现。

### 4.5 后端：收敛契约，补两块能力

1. **契约清理**：以 `snake_case` 为唯一规范；删除 `PartSummary` 的 camelCase 重复字段；所有路由补 `response_model`；重新生成 `clients/sdk/api.d.ts`。
2. **社区接口接入小程序**：`/posts`、`/posts/{id}`、`/posts/{id}/comments`、`/votes`、`/leaderboard` 已存在，小程序补页面即可。
3. **新增选型能力**：`/selection/facets`（多维 facet）、`/selection/bom`（BOM 兼容校验），数据仍来自 release 投影，不新增写域。
4. **新增 AI 助手**：`/assistant/query`，返回 `answer + citations[] + confidence + trace`；索引由同一 `data-v*` 快照构建；低置信直接拒答。**不做模型代理**，只做薄层。
5. **描述修正**：`backend/app/main.py` 的 API 描述改为当前定位；保留 `/api/v1` 与 `/api` 别名策略。

### 4.6 数据与 AI 链路

```text
data-v* release
   ├─ pipeline build → 静态页 / 分享 JSON / 图片
   ├─ API 投影 → parts / materials / builds
   └─ RAG 索引 → 参数切片 + 来源 + part_id + field
                         │
                         ▼
              /assistant/query → 答案 + 引用（part/field/source_tier/url）
```

**引用是硬要求**：每条 AI 答案必须能点回「哪个部件、哪个字段、哪份来源、什么等级」。没有引用就不回答。

## 6. 双端体验统一方案

### 6.1 统一信息架构

- 一级入口固定为「学习 / 方案 / 部件 / 社区 / 采购」（小程序用 tab 表达）。
- 所有列表页统一「标题 + 一句话说明 + 统计条 + 筛选 + 列表 + 空态」。
- 所有详情页统一「标题区（型号/厂商/等级/核对）→ 关键参数 → 全部参数 → 来源 → 讨论/评分」。
- 工具页（搜索、对比、路径选择、开源索引、站务、登录、账号、社区、帖子）**不挂评论区**。

### 6.2 统一设计系统

| 项 | 现状 | 目标 |
|---|---|---|
| 颜色 | 小程序硬编码 `#0f172a` | 全部 `var(--rw-ink)` / `--rw-*` |
| 深色 | 仅网页 | 小程序用 `page.dark` + 主题设置 |
| 字体 | 两端不同 | 统一 `var(--rw-font-sans)` / `--rw-font-mono` |
| 控件 | 网页 antd/Tailwind，小程序手写 | 同一 props 的 `ui-web` / `ui-taro` |
| 状态 | 空态/错误/加载各写 | 统一 `EmptyState` / `ErrorState` / `Skeleton` |
| 触控 | 小程序部分 <44 | 触控目标 ≥44px |

### 6.3 统一内容模型

- 部件卡片：`vendor → model → 关键参数 → 价格/询价 → 评分 → 来源等级`。
- 评分：`n=0` 显示「暂无评分」；`n<3` 显示「样本不足」；不显示假 0 分。
- 缺失：一律 `null` / 「—」/「询价」，不补 0、不猜。
- 讨论：最多 2 层缩进，更深平铺并标注「回复 @xxx」。
- 通知：单一入口 + 未读角标，列表分「全部 / 未读」。

### 6.4 减少「内容混杂」的具体做法

1. **社区升级为一级入口**：网页主导航加「社区」，小程序加 tab。
2. **讨论区折叠**：内容页底部用「讨论（N）」折叠区，默认收起；移动端改为详情页的「讨论」tab。
3. **阅读与操作分离**：部件页正文只留「参数 + 来源」；评分/讨论/纠错放到独立区块或吸底操作栏。
4. **页脚收敛**：页脚只保留「关于 / 来源 / 免责声明 / GitHub」，不再承担二级导航。
5. **工具页去噪**：搜索、对比、路径选择等页面不挂评论、不挂推荐。

### 6.5 移动优先的部件页

- 顶部：图片轮播 + 型号/厂商/等级/核对。
- 中部：关键参数 3–5 项 + 「查看全部参数」。
- 吸底操作栏：`对比` / `评分` / `纠错` / `分享`。
- 讨论：独立 tab，避免正文过长。
- 性能：图片懒加载 + 骨架屏 + 首屏 < 2s。

## 8. 指标与风险

### 8.1 核心指标

| 维度 | 指标 | 目标 |
|---|---|---|
| 任务 | 搜索 → 详情 → 对比/BOM → 投稿 的完成率 | 逐季提升 |
| 双端 | 移动端占比、7 日留存 | 小程序承接「现场查件」 |
| 贡献 | 每 100 次访问的评分/评论/投稿数 | 提升 |
| 数据 | A 级占比、`null` 率、来源覆盖率 | 可追溯性可量化 |
| 社区 | 首响时间、采纳率、审核 SLA | 健康度 |
| AI | 引用准确率、拒答率、单次成本 | 可信优先 |

### 8.2 风险与取舍

| 风险 | 说明 | 对策 |
|---|---|---|
| Astro vs 纯 React | 用户可能要求「前端基于 React」 | 说明 Astro 内已是 React 19 岛；如必须统一，先 ADR、只迁交互层 |
| 双端对齐成本 | 小程序从 5 页到 ~15 页 | 用 `packages/features` 复用逻辑，分 Phase 交付 |
| 内容治理 | 社区开放后广告/不实信息 | 先审后发、举报、站务后台、A/B/C 来源约束 |
| AI 幻觉 | 选型建议错误代价高 | 强制引用、低置信拒答、人工复核入口 |
| 许可证 | New API AGPL、Vendure/Reaction GPL | 不 fork；只借鉴模型与交互 |
| 数据版权 | 厂商手册/商品图 | 保持 `image_source` / `repo_license` / `NOTICE` |
| 规模数字漂移 | README 与页面条数滞后 | 以 `data.lock.json` counts 为准 |
